# openshell-work

Toolbox for running pi inside OpenShell sandboxes: container image build,
provider/credential setup, sandbox creation, host<->sandbox sync.

## Layout

| Path | Role |
|---|---|
| `Containerfile` | Fedora 45 image: dev tools, Node 24, pi + MCP servers baked in globally, pi packages pre-installed under `/workspace/.pi/agent` |
| `build.sh` | Stages host pi config into `pi-config/`, applies sandbox-specific transforms, runs `podman build` → `localhost/pi-fedora:latest` |
| `transform-models.mjs` | Rewrites `!secret-tool lookup service X` apiKey entries in the baked `models.json` to `$X_API_KEY` env vars (host file keeps keyring lookups) |
| `sandbox-overrides/agent/mcp.json` | Sandbox version of pi's mcp.json (host one points at host paths); overrides win during build staging |
| `providers.sh` | Imports provider profiles + creates/refreshes provider instances (exa, context7, jira-cloud, github-mcp, enmaas, rhcorp-qwen). Run once, and again on credential rotation |
| `profiles/*.yaml` | Provider profile definitions (exa, context7, jira-cloud, github-mcp, enmaas, rhcorp-qwen); import is idempotent and preserves the server's `resource_version` |
| `policy.yaml` | Sandbox filesystem + network policy (read-only system paths, rw `/tmp`; inference endpoints with `tls: skip`) |
| `create.sh` | Create single `pi-dev` sandbox from the local image (with all providers), drop into pi |
| `create-many.sh` | Create one sandbox per work area (default: `pi-openshift pi-openstack pi-llm`), each running a tmux session `work`, 2 CPU / 4Gi |
| `sync.sh` | Two-way dir sync host<->sandbox: `push` / `pull` / `diff` |
| `run.sh` | One-shot pi run on any local repo checkout: `up` / `down` / `run` / `status` (see below) |
| `pi-config/`, `workspace/` | Build-time staging dirs (generated by `build.sh`; regenerated on each build) |

## Normal workflow

```bash
bash run.sh build                           # rebuild pi image (after config changes)
bash run.sh up ~/work/myrepo                # sandbox + upload + pi as main process, in the repo
#   in pi: Ctrl-P Ctrl-Q detaches (pi keeps running)
#   reattach: openshell sandbox connect <name>; extra shells: run.sh status lists the name
bash run.sh down ~/work/myrepo              # pull changes back (works detached or after exiting pi), delete sandbox
bash run.sh up ~/work/myrepo --exec         # old model: one-shot exec pi (dies on disconnect)
bash run.sh run ~/work/myrepo --print "..." # one-shot non-interactive pi (up -> pi -> down)

# or the original long-lived-sandbox flow:
bash create-many.sh                         # create sandboxes (skips existing ones)
openshell sandbox connect pi-llm
# sync code between host and a sandbox
bash sync.sh diff  pi-llm ./local-dir /workspace/remote-dir
bash sync.sh push  pi-llm ./local-dir /workspace/remote-dir
bash sync.sh pull  pi-llm ./local-dir /workspace/remote-dir
```

Extra shells in a sandbox: `ssh openshell-<name>.default` then `tmux attach -t work`
(SSH host aliases are added to `~/.ssh/config` by `openshell sandbox ssh-config`).
The legacy `build.sh`/`create.sh`/`create-many.sh`/`providers.sh` flow still works
unchanged; `run.sh build` just wraps `build.sh`.

## run.sh details

Start it from anywhere; `[dir]` defaults to cwd. `build` rebuilds the image.
`up` requires it (no implicit build), creates a sandbox with all providers +
`policy.yaml`, then tars the tree (tracked + non-ignored untracked + `.git`,
so pi can commit; linked worktrees/submodules aren't handled — the CLI's own
`--upload` filters relative to the CLI's cwd, so the script does its own
NUL-safe file list), uploads the tar through the gateway, and extracts it in
the sandbox; copies git identity from the repo's effective config into
the sandbox, then starts pi as the canonical main process in the repo (a
waiter holds it until the upload lands; reattach after Ctrl-P Ctrl-Q with
`openshell sandbox connect`). If you exit pi, the sandbox stops — `down`
detects that and restarts it (workspace preserved) before pulling. `down` brings sandbox changes
back: commits via `git bundle` -> `git fetch` -> `--ff-only` merge (on conflict
the bundle is kept as `./.run-state/<repo>.env.bundle`), uncommitted files via a
sandbox-side tar of `git status`. Sandbox-side deletions don't propagate (tar
skips missing files); host edits made while the sandbox ran may be overwritten.
State (sandbox name, paths, up-time HEAD) lives in `./.run-state/<repo>.env`, so
up and down can run in separate invocations. Transfers go through the gateway
(`upload`/`download`), never SSH.

## Required .env

Templates (`policy.yaml`, `profiles/enmaas.yaml`, `profiles/rhcorp-qwen.yaml`,
`sandbox-overrides/agent/mcp.json`) carry `${VAR}` placeholders. Create a
 gitignored `./.env` with the real values before building/creating/importing
(`common.sh` renders them at use time):

```bash
INFERENCE_HOST_1=<inference endpoint 1>   # policy.yaml
INFERENCE_HOST_2=<inference endpoint 2>   # policy.yaml
ENMAAS_HOST=<enmaas api host>             # profiles/enmaas.yaml
QWEN_HOST=<qwen api host>                 # profiles/rhcorp-qwen.yaml
JIRA_BASE_URL=<jira url>                  # sandbox mcp.json
JIRA_EMAIL=<your email>                   # sandbox mcp.json
```

## Gotchas

- **Config is baked, not mounted.** `pi-config/` and `workspace/` are copied into
  the image at build time from `$HOME/.pi/agent` + sandbox overrides. Changing
  host pi config requires `build.sh` + sandbox recreate, or push via
  `sync.sh`/`openshell sandbox upload`.
- **`transform-models.mjs` runs only on the baked copy** — host `models.json`
  keeps `!secret-tool` entries; sandbox gets `$*_API_KEY` env vars injected by
  the providers created by `providers.sh`.
- **`pi-sandbox` package is stripped** from the baked settings.json — it drives
  local podman and is host-side only.
- **SSH transfer limit:** the supervisor's pending-stdin buffer is 4 MiB; big
  transfers fail with exit 74 ("process stdin buffer is full"). `sync.sh`
  throttles rsync with `--bwlimit` (raise via `SYNC_BWLIMIT`), or use
  `SYNC_TAR=1` (tar pipe over SSH) / `SYNC_GATEWAY=1` (routes through
  `openshell sandbox upload/download`, never touches SSH).
- **`build.sh` needs network** (`--network=host`) for dnf/npm at build time;
  runtime network is restricted by `policy.yaml`.
- `providers.sh` reads secrets from `secret-tool` (host keyring) unless the
  matching env var is already set.
